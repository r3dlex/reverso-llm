# Ollama provider for Claude Code and Codex

## Status

- **Type:** implementation handoff / planning artifact
- **Status:** ready for discovery spike; implementation not started
- **Owner:** Reverso provider/configuration work
- **Scope:** direct Ollama integration for Claude Code and Codex

## Objective

Expose Ollama as a first-class selectable provider for both Claude Code and
Codex, supporting local models and Ollama Cloud models while preserving
Ollama's ownership of authentication, cloud routing, model availability, and
Ollama-specific tools such as web search.

The integration should be managed by Reverso's client synchronization layer,
but Ollama requests must not be routed through a new Reverso gateway adapter.

## Evidence and repository context

Ollama documents the following integration surfaces:

- Claude Code through the Anthropic-compatible API at the Ollama endpoint,
  using `ANTHROPIC_AUTH_TOKEN=ollama`, an empty `ANTHROPIC_API_KEY`, and
  `ANTHROPIC_BASE_URL`.
- Codex through `ollama launch codex`, `codex --oss`, or a profile using an
  Ollama provider with `wire_api = "responses"` and a `/v1/` base URL.
- Cloud model identifiers use Ollama model naming and remain controlled by
  Ollama after `ollama signin`.
- Coding workloads should use a context window of at least 64k tokens.

Current Reverso seams:

- `src/reverso/claude_code_sync.py` generates managed Claude Code launchers.
- `src/reverso/codex_sync.py` generates Codex profiles and model catalogs.
- `src/reverso/protocols/model_exposure.py` owns provider prefixes, selector
  collision rules, display names, and Codex profile metadata.
- `src/reverso/client_sync.py` owns convergence groups and dependency order.
- `config/supported-client-surfaces.json` freezes the installed surface
  contract.
- Existing unit tests cover idempotence, locks, backups, ownership, archival,
  catalog refresh, and client convergence.

## Decisions

1. **Direct external provider:** Ollama is not added to the Reverso-routed
   provider adapter set.
2. **Credential boundary:** Ollama authentication stays in Ollama. Reverso
   must not copy, persist, or proxy `OLLAMA_API_KEY`.
3. **Selector namespace:** use `ollama/<model>` for Codex and
   `ollama-<model>` for Claude Code to avoid collisions with built-in and
   existing provider model IDs.
4. **Default endpoint:** use the local Ollama control plane, configurable for
   non-default deployments. Cloud routing remains an Ollama concern.
5. **Catalog authority:** prefer the catalog generated by
   `ollama launch codex --config`; only generate a Reverso-owned catalog if
   the discovery spike proves that Ollama's catalog cannot be referenced or
   refreshed safely.
6. **No fallback:** an unavailable or unauthenticated Ollama runtime must fail
   clearly; it must not silently route to Reverso, OpenAI, or another provider.

## Non-goals

- Adding an Ollama Responses or Anthropic adapter to the Reverso gateway.
- Storing Ollama credentials in Reverso configuration, launch agents, or
  generated catalogs.
- Hard-coding a permanent list of Ollama models.
- Making Ollama the default Claude Code or Codex provider.
- Guaranteeing that every Ollama model supports tools, vision, thinking, or
  64k+ context.
- Reimplementing Ollama web search inside Reverso.

## Implementation plan

### Slice 1 - Ollama discovery spike

Inspect the installed Ollama behavior without modifying production files:

```shell
ollama --version
ollama list
ollama launch codex --config
ollama launch claude --help
```

Record:

- generated Codex profile and catalog paths;
- catalog JSON schema and ownership markers;
- whether `/v1/models` includes local and cloud models;
- behavior before and after `ollama signin`;
- local versus `:cloud` model names;
- endpoint behavior when Ollama is stopped;
- minimum Ollama and Codex versions;
- whether the generated profile is safe to reference from Reverso-managed
  configuration.

The spike must not require cloud credentials in CI and must produce a written
decision on catalog ownership before implementation proceeds.

### Slice 2 - Central provider policy

Update `src/reverso/protocols/model_exposure.py`:

- add `ollama` to the external-provider policy;
- add `ollama/` Codex selector names;
- add `ollama-` Claude Code selector names;
- add display-name handling;
- define context-window metadata with a 64k minimum recommendation;
- keep Ollama outside `REVERSO_ROUTED_CODEX_PROFILE_PREFIXES`;
- define whether model IDs are exposed unchanged or normalized for selectors.

Update capability metadata only for features that Reverso itself enforces.
Ollama-native web search and model-specific capabilities should remain outside
the Reverso gateway parity table unless a client-surface contract requires
otherwise.

### Slice 3 - Claude Code launcher

Extend `src/reverso/claude_code_sync.py` with a managed `claude-ollama`
launcher:

- set `ANTHROPIC_AUTH_TOKEN=ollama`;
- set `ANTHROPIC_API_KEY` to an empty value;
- set configurable `ANTHROPIC_BASE_URL`;
- pass the selected Ollama model;
- preserve unrelated Claude settings and user-owned launchers;
- use the existing managed-launcher marker, lock, atomic write, and archival
  behavior;
- scrub Reverso-specific environment variables so the launcher cannot loop
  back through Reverso.

The launcher must work for both local and `:cloud` model IDs without assuming
that Reverso can inspect the user's Ollama account.

### Slice 4 - Codex profile and catalog

Extend `src/reverso/codex_sync.py` with an external Ollama profile:

- profile name: `ollama.config.toml`;
- provider name: `ollama-launch` unless the discovery spike proves a better
  stable name;
- `wire_api = "responses"`;
- base URL ending in `/v1/`;
- selected local or cloud model;
- 64k+ context metadata where supported by the installed Codex version;
- catalog reference or generation according to Slice 1;
- no modification of Codex's default OpenAI profile.

If Reverso must generate the catalog, use Ollama's OpenAI-compatible model
listing as the source, preserve local/cloud IDs exactly, and apply the same
ownership, atomic-write, backup, and unmanaged-file safeguards as existing
provider catalogs.

### Slice 5 - Client convergence contract

Update the convergence model:

- add `provider-ollama` to `src/reverso/client_sync.py`;
- add `claude-ollama` and `codex-ollama` to
  `config/supported-client-surfaces.json`;
- define dependency ordering for shared Claude and Codex configuration;
- update install, refresh, restore, and uninstall behavior;
- update contract fixtures and drift checks;
- ensure a failed Ollama refresh cannot partially rewrite other providers.

### Slice 6 - Tests

Add deterministic tests for:

- Claude launcher environment and model argument rendering;
- local and `:cloud` model identifiers;
- custom Ollama endpoint handling;
- Codex profile rendering and `wire_api = "responses"`;
- `ollama/<model>` and `ollama-<model>` selector naming;
- catalog reference/generation behavior;
- unavailable Ollama and malformed model responses;
- credential non-persistence;
- user-owned profile/catalog preservation;
- idempotent sync and restore;
- client convergence manifest parity.

All tests must use temporary paths and injected fetchers or subprocess
boundaries. CI must not require Ollama, Ollama Cloud, or a signed-in account.

### Slice 7 - Documentation and live proof

Document installation and operation in the existing Reverso documentation:

- Ollama installation and sign-in;
- local versus cloud model selection;
- generated launcher/profile names;
- context-window requirements;
- web-search ownership;
- restore/uninstall behavior;
- failure behavior when Ollama is unavailable.

Run a live proof on the target machine for one local model and one cloud model,
covering both Claude Code and Codex. Record model IDs, selected profiles,
successful request evidence, and cleanup/restore evidence without publishing
credentials or prompt contents.

### Slice 8 - Automatic background Ollama service

Provide an opt-in, macOS-specific service-management path for running
`ollama serve` in the background automatically.

The service must be treated as an external prerequisite, not as a Reverso
gateway process:

- detect whether the Ollama desktop application or another `ollama serve`
  process already owns the configured endpoint;
- do not start a second server when Ollama is already serving;
- install a user-level LaunchAgent only when explicitly enabled;
- use a stable label such as `com.user.ollama-serve`;
- use `RunAtLoad = true` and `KeepAlive = true` with a restart throttle;
- invoke an absolute, validated `ollama` executable path;
- pass configurable host/context settings through the LaunchAgent environment;
- write bounded stdout/stderr logs under the user's Ollama/Reverso log area;
- keep Ollama authentication and cloud credentials out of the plist;
- provide idempotent install, status, stop, restore, and uninstall operations;
- unload only the LaunchAgent managed by this integration;
- never terminate or modify a user-owned Ollama desktop process;
- fail clearly when the endpoint is already occupied by a non-Ollama process.

The default behavior should remain non-invasive: if the user has not enabled
service management, generated Claude Code and Codex surfaces should report
that Ollama is unavailable rather than silently installing a daemon.

The implementation should reuse Reverso's existing LaunchAgent conventions and
mutation safety patterns where appropriate, but must keep the Ollama service
artifacts separate from Reverso's gateway and catalog-refresh services.

Service-management tests must use temporary plist and executable paths, mocked
process checks, and a fake `ollama serve`; CI must not start a real daemon.

## Acceptance criteria

- `claude-ollama` launches Claude Code against Ollama without Reverso routing.
- `ollama.config.toml` launches Codex against Ollama using Responses API wiring.
- Both local and cloud model IDs remain selectable without hard-coded provider
  assumptions.
- Codex selectors are provider-scoped as `ollama/<model>`.
- Claude Code selectors/launchers are provider-scoped as `ollama-<model>`.
- Ollama credentials remain outside Reverso-managed files.
- Existing Claude, Codex, and Reverso provider behavior is unchanged.
- User-owned configuration and catalogs are preserved.
- Sync, refresh, restore, and uninstall are idempotent and atomic.
- When enabled, `ollama serve` starts automatically in the background through a
  managed user LaunchAgent and is restarted after unexpected exit.
- When disabled, Reverso does not install, stop, or modify an Ollama service.
- Existing Ollama desktop/server processes are detected and never duplicated
  or terminated by cleanup.
- Unit and contract tests pass without Ollama installed.
- Live proof succeeds for one local and one cloud model, or the unsupported
  capability is documented as an explicit blocker.

## Risks and unresolved questions

1. Can the Ollama-generated Codex catalog be referenced safely, or must Reverso
   copy/own a catalog?
2. Does Ollama's `/v1/models` endpoint expose cloud models consistently after
   sign-in?
3. Which Ollama endpoint does the installed `ollama launch` command generate
   for cloud-backed models?
4. Does the installed Codex version accept all Ollama-generated profile keys?
5. How should model-specific capability gaps be surfaced without duplicating
   Ollama's catalog metadata?
6. Does Claude Code require any additional headers or settings for current
   Ollama Anthropic compatibility?
7. Does the Ollama desktop application already install its own LaunchAgent or
   service manager on the target macOS version?
8. Should service management be enabled by an explicit installer flag, a
   config setting, or both?
9. Which `OLLAMA_HOST` and context-length environment settings are supported
   by the installed Ollama version when launched by `launchd`?
